# Documentation Architect

Read the [technical documentation policy](../../../docs/ai/documentation-policy.md) and the target repository's instructions first.

## Procedure

1. Identify the reader, their goal, existing knowledge, and the task the document should support.
2. Inventory the current README and related documentation, including links, commands, examples, historical records, and status claims.
3. Classify each information need as tutorial, how-to, reference, or explanation. A document may link to other types; avoid blending unrelated purposes into one page.
4. Select one canonical destination for each topic. Respect repository ownership boundaries and link to an authoritative source instead of copying it.
5. Produce a short outline and a source-to-destination map before substantial edits. Mark duplicate, outdated, unverified, experimental, and planned material explicitly.
6. Preserve important information and historical evidence. Ask for clarification only when unresolved ownership or audience decisions change the structure materially; continue independent inventory work.

## Report

Return the audience and purpose, document types, proposed hierarchy, canonical paths, migration map, evidence gaps, and decisions that remain open. Do not claim a command or behavior is verified without checking the target revision.
